# 方法论：为什么是"脚本转录 + 大模型后处理"两阶段

这份文档解释本 skill 最核心的一个设计决定，以及它带来的几条硬性约束。

## 一句话结论

语音模型负责**声音 → 带时间戳的粗糙文字**，大模型负责**粗糙文字 → 可读文稿**。两件事必须由两个不同的组件做，中间用一份**不做任何清理**的 JSON 交接。

## 为什么不在转录阶段就清理干净

一个很自然的想法是：既然 Whisper 输出的文字有语气词、没标点、断句奇怪，那就在 `transcribe.py` 里加一层规则清理 —— 去掉"呃""那个"，按时间间隔加句号，每 30 秒分一段。

这条路走不通，原因有三个：

**1. 清理会销毁后处理需要的信息。**

时间间隔是判断句读的重要依据：两个 segment 之间停了 1.2 秒，很可能就是句号；停了 0.1 秒，多半是逗号。如果在脚本里先把 segment 合并成整段文字，大模型就拿不到这些间隔了 —— 它只能靠语义猜标点，而语义猜标点在长难句上经常猜错。

同理，"呃这个呃项目的话"里的重复语气词，是判断说话人犹豫、强调、自我修正的线索。会议纪要里"这个方案……我觉得还是要再评估一下"的迟疑，删掉语气词后就变成了干脆的"这个方案要再评估"，语气完全变了。

**2. 规则清理的错误是不可见的，大模型清理的错误是可追溯的。**

规则脚本删掉的东西，下游没人知道它删了什么。而大模型后处理时，原始的 `segments` 数组还在 JSON 里，用户随时可以对照 `*.timeline.txt` 检查"这句话原文到底是什么"。**保留原始态就是保留可追溯性。**

**3. 两件事的失败模式不同，混在一起会互相掩盖。**

转录失败是确定性的（模型没识别出来），后处理失败是概率性的（大模型理解偏了）。如果混成一步，一份有问题的文稿你分不清是"没听清"还是"理解错" —— 而这两种情况的应对完全不同：前者要换模型或重录，后者要改提示词或人工重写。

## 所以第 3 步刻意"什么都不做"

`transcribe.py` 的输出契约里有几条看起来很"懒"的规定，其实都是刻意的：

- **不加标点** —— 原始转录几乎没有标点，这是正常的，留给第 5 步
- **不去语气词** —— "呃""那个""就是说"全部保留
- **不合并 segment** —— 按识别引擎的换气停顿切分，一段一个对象
- **不重新分段** —— segment 边界是声学边界，不是语义边界
- **只做两件极轻的规整**：文本 `strip()`、空文本分段丢弃

唯一做的规整都是为了下游好处理，不损失任何信息。

## 第 5 步为什么不用脚本

反过来问：既然后处理这么重要，为什么不写个 `postprocess.py`，用规则或者调 LLM API 做掉？

因为**这一步的核心能力恰好是语言模型的强项，而且是规则脚本永远做不好的那部分**：

| 任务 | 规则脚本能做到吗 |
|---|---|
| 判断"在"和"再"哪个对 | 不能，要看上下文语义 |
| 判断一句话该在哪断开 | 勉强，靠标点和连词，长难句必错 |
| 识别话题转折点并分段 | 不能，这是语义理解 |
| 提炼 3-5 句摘要 | 完全不能 |
| 修正专有名词的同音错字 | 不能，需要世界知识 |
| 判断哪句是决议、哪句是待办 | 不能 |

写一个 `postprocess.py` 去调 LLM API 是可行的，但那会引入 API key 管理、网络依赖、成本控制、速率限制一整套复杂度，而**在 agent 场景里这个能力本来就在手边** —— 对话中的大模型直接读 JSON 就能做，零额外依赖，零额外成本，还能结合用户的即时要求（"只要摘要不要正文""按发言人分段""重点标出数字"）。

所以第 5 步是**给 agent 的指令，不是给机器的脚本**。这也是为什么 `SKILL.md` 里第 5 步写得比前四步都细 —— 它是一份 prompt，不是一份 API 文档。

代价是：脱离 agent 环境（比如纯 cron 批处理）时第 5 步无法自动完成。这记在「已知局限」里，v0.2 可以补一个可选的 LLM API 版后处理脚本。

## 第 4 步（校验）为什么必须存在

两阶段架构有个隐藏风险：**中间那份 JSON 是唯一的交接物**。如果它是残缺的，第 5 步会怎样？

大模型拿到 `segments: []` 或者时间戳错乱的 JSON，**不会报错，它会编**。它会写出一份格式完美、语气通顺、摘要像模像样的 Markdown 文档 —— 内容全是幻觉。这比脚本直接崩掉危险得多，因为用户看不出问题。

`scripts/validate.py` 就是为了堵这个口子。它在交接物上设了一道闸：

- 字段完整性（8 个顶层字段 + 5 个 source 字段）
- `ok` 必须为 `true`（失败结果不能被当成转录产物）
- 时间戳单调递增、`end >= start`、末段不超总时长
- 文本必须是非空字符串
- `segment_count` 与实际长度一致
- `segments` 非空

任何一条不过就 FAIL，退出码 1，**流程必须停下来**。

还有一条同样重要的性质：**校验器自己绝不能崩在畸形数据上**。v0.1 的校验器有两处会：所有 segment 的 `end` 都非法时 `max()` 收到空序列报 `ValueError`；`text` 是 int 时 `len()` 报 `TypeError`。一个校验器崩在它本该拒绝的输入上，等于把闸门变成了新的故障点。现在有 18 组参数化用例专门守这条性质。

## 这套方法论带来的硬性约束

以下每条都有测试或 CI 把守，改动前请先看对应的测试：

1. **stdout 只有一个 JSON 对象** —— 进度、下载日志、告警全部走 stderr。破坏这条会让所有机器消费方失效。
   → `tests/test_stdio_contract.py`

2. **第 3 步不做语义清理** —— 加标点、删语气词、合并 segment 都属于越界。
   → `tests/test_transcribe_core.py::TestTranscribeResultShape`（只允许 strip 和丢空段）

3. **原始 JSON 必须落盘保留** —— 它是可追溯性的凭据，不能只在 stdout 上一闪而过。
   → `tests/test_render.py::TestWriteOutputs`

4. **错误必须结构化** —— `{code, message, hint}` 三件套，`hint` 要能照做。
   → `tests/test_stdio_contract.py::TestCliStdoutIsPureJson`

5. **阻塞与告警必须分开** —— 缺 ffmpeg 不该拦停流程（PyAV 自带解码库）。把软依赖判成阻塞项会误伤本来能跑的场景。
   → `tests/test_env_check.py::TestCheckFfmpeg`

6. **校验器不得因输入畸形而抛异常** —— 只能返回 FAIL。
   → `tests/test_validate.py::TestValidatorNeverCrashes`

7. **贪心解码，不采样** —— `temperature: 0.0`。转录要的是可复现，不是创造性。同一份音频两次运行应该得到同一份文字。
   → `config/transcribe_config.yaml` + `tests/test_transcribe_core.py::TestBuildTranscribeKwargs`
